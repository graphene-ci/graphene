# Форма

Из чего система состоит и кто что где выполняет. Обоснования решений
здесь же — чтобы через месяц не переспорить их заново по памяти.

Видение — в `VISION.md`. Здесь только устройство.

## Что где стоит

**В инсталляции:** k3s; Temporal со своей базой; Crossplane с провайдерами
тех облаков, которые нужны пользователю; наши операторы; системный воркер;
воркеры пайплайнов — по одному деплойменту на версию образа.

**На машине:** агент — Temporal-воркер, читающий очередь со своим именем.
Больше ничего.

**У человека:** `graphene` — и инструмент разработчика (`generate`,
`build`), и клиент (запустить, смотреть). Позже UI, делающий то же самое.

## Кто что выполняет

| Кто | Где | Что делает | Что имеет |
|---|---|---|---|
| воркер пайплайна | в кластере, деплоймент на версию образа | только решает | ничего: ни куба, ни облака, ни секретов |
| системный воркер | в кластере, наш | пишет записи, кладёт артефакты, разрешает секреты | доступ к кубу и секретам |
| наши операторы | в кластере | `Run`, `Stand`, `MachineIntent`, `Pipeline`, `PipelineRevision`, `Artifact`: доводят до мира, ставят готовность, будят воркфлоу | по своим видам |
| контроллеры Crossplane | в кластере | облачные ресурсы | доступ к облаку |
| агент | на машине | выполняет команды и шаги | только свою очередь |
| Temporal | в кластере | ход дела: попытки, повторы, отмена, история | — |
| k8s | он же | правда о мире: что есть, чьё, готово ли | — |

## Пример пайплайна

Набросок для разбора формы, не финальный API.

```go
import (
	"github.com/graphene-ci/graphene/sdk/pipeline"      // наш SDK
	graphenev1 "github.com/graphene-ci/graphene/sdk/api/v1" // наши виды: Machine, Stand, Artifact
	yandexv1  "github.com/crossplane-contrib/provider-yandex/apis/compute/v1beta1"
	"acme/perf"                                         // код пользователя
)

func main() { pipeline.Serve(Perf) }

type Params struct {
	Nodes   int    `graphene:"nodes,default=3"`
	Version string `graphene:"pg_version,default=16"`
}

func Perf(run pipeline.Run, p Params) (err error) {
	// [воркер пайплайна] снос при любом конце, включая отмену
	defer func() { run.Teardown(err) }()

	// МЫ НИКОГДА НЕ ХОДИМ НА МАШИНУ — машина приходит к нам. Скрипт
	// установки отдаёт SDK, а кладёт его пользователь в СВОЮ спеку: имя
	// поля знает он, мы про провайдера по-прежнему не знаем ничего.
	vms := make([]pipeline.Ref[*yandexv1.Instance], p.Nodes)
	nodes := make([]pipeline.Target, p.Nodes)

	for i := range vms {
		// [системный воркер] выпустил пропуск, вернул текст скрипта и имя
		// очереди. Запись Machine появится сама, когда агент представится.
		join := agent.Install(run, fmt.Sprintf("node-%d", i))

		// [воркер пайплайна] решил
		// [системный воркер] apply записи (создать-или-найти по имени)
		// [контроллер Crossplane] создал ВМ
		vms[i] = pipeline.Apply(run, fmt.Sprintf("node-%d", i), &yandexv1.Instance{
			Spec: yandexv1.InstanceSpec{
				Cores: 4, MemoryGB: 16,
				UserData: join.CloudInit(),   // ← поле провайдера, не наше
			},
		})
		nodes[i] = join
	}
	// Готовности ВМ не ждём и агента не ждём: очередь и есть ожидание, а
	// подключившийся агент и есть доказательство, что машина работает.
	// Никто не подключился — шаг падает по ScheduleToStart с внятной
	// причиной.

	// [агент на node-0] выполняет; секрет идёт ссылкой, значение
	// разрешается у него
	install := pipeline.On(run, nodes[0]).Command("install-pg",
		perf.InstallScript(p.Version),
		pipeline.Uses(graphenev1.SecretRef("pg-admin")),
	)
	if install.Code != 0 {
		return fmt.Errorf("установка не прошла: %s", install.Tail)
	}

	bench := pipeline.On(run, nodes[0]).Step("bench", perf.Bench(p))

	// [системный воркер] данные в хранилище, в записи — ссылка и дайджест
	pipeline.Artifact(run, "bench-report", bench.Report)

	if bench.P99 > perf.Threshold {
		run.Keep(24 * time.Hour) // стенд остаётся, прогон кончается
		return fmt.Errorf("деградация: p99 %v", bench.P99)
	}
	return nil
}
```

Импорты — четыре разных источника, и это видно по префиксу: наш SDK, наши
виды, чужой провайдер, код пользователя.

## Решения формы

### Вход — запись, а не запуск воркфлоу

Человек создаёт `Run`; оператор видит запись и стартует воркфлоу. Не
наоборот.

Тогда «кто может запускать» — обычный RBAC на создание `Run`, и вход один
для CLI, UI и любого триггера. Если входом был бы Temporal, права пришлось
бы держать в двух местах с первого дня.

### `Run` не исчезает; владеет `Stand`

`Run` меняет статус и остаётся — иначе история невосстановима.

Владение вешается на `Stand` — запись, чьё удаление и означает «стенда
больше нет». Прогон создаёт стенд, ресурсы принадлежат стенду, `Run` живёт
дольше и хранит, чем всё кончилось.

- снос — удалить `Stand`, дальше работает сборщик мусора;
- оставить — не удалять, поставить срок: это и есть `run.Keep(24h)`;
- передать — сменить владельца на долгоживущую запись.

Отсюда следует то, что нельзя забыть: **у `Run` должен быть свой срок
хранения**, иначе прогоны копятся в etcd навсегда.

### Агента как вида нет; очередь — свойство машины

Агент — это процесс, а не запись. Запись одна — `Machine`, — и в ней
среди прочего лежит имя очереди, которое агент назвал, когда представился.
Заводить отдельный вид ради того же самого значило бы держать две записи об
одной железке и следить, чтобы они не разошлись.

**Ожидания агента перед шагом нет.** Очередь и есть ожидание: шаг
отправляется, Temporal держит его, пока не появится тот, кто читает; не
дождался — падает по `ScheduleToStart` с сообщением лучше нашего:
«выполнять было некому». Свой `Await` делал бы то же самое руками и
добавлял второе место, где можно залипнуть.

**Шаг адресуется очередью, а не записью.** Запись нужна для другого — для
**выбора и видимости**: пул машин, «выполни на любой с меткой
`pg-runner`», `kubectl get`, права. Очереди Temporal по меткам не
выбираются, записи выбираются — ради этого кубер и существует.

Поэтому `Ready` у `Machine` значит **«годится для выбора»**, а не «можно
начинать». Меряется дёшево — `coordination.k8s.io/Lease`, тем же способом,
которым живёт kubelet: агент продлевает аренду, готовность снимается после
трёх пропусков. Свой heartbeat прямо в статус не годится — это запись на
машину на такт, ровно та беда, из-за которой шаги не стали записями.

**Два срока независимы.** Снятие готовности не трогает идущий шаг, и
наоборот: пятисекундное моргание сети не должно убивать часовой тест,
который прекрасно идёт на машине. Судьба начатого — таймауты Temporal
(`HeartbeatTimeout`, политика повторов по типу шага); готовность — про то,
можно ли **начинать** новое.

Машина умерла посреди шага — activity падает, и дальше это обычная ошибка
в программе: сделать новую машину и повторить, свернуться, оставить стенд.
**Реакция на смерть машины пишется как код, а не настраивается галочкой** —
лучшая иллюстрация, зачем взят настоящий язык.

### Машины: два вида, потому что владение разное

**`MachineIntent`** — заявка: «вот ssh-координаты, возьми машину под
управление». Её написал человек или прогон, у неё есть владелец и конец,
её можно удалить, когда выполнена.

**`Machine`** — то, что подключилось. Ничья: появилась, когда агент
представился, и живёт, пока он жив.

Почему не одна запись со спекой и статусом: заявка, написанная прогоном,
была бы прогоном и удалена — а железка осталась, агент на ней работает и
тут же зарегистрирует её снова. Владение у этих двух разное, значит и
записи разные.

(`MachineClaim` как имя отброшено намеренно: рядом стоит аренда, которая и
есть claim, и два claim'а в одном словаре перепутают.)

**`Machine` регистрируется агентом**, как `Node` регистрируется kubelet-ом.
Для облачной ВМ отдельно писать её не надо: подключившийся агент заведёт
запись сам и расскажет, что он такое. Пайплайн пишет только ресурс
провайдера — то, что он и хотел создать.

Способности — двух происхождений, и путать их нельзя:

- **обнаруженные** пишет агент: `os=linux`, `arch=amd64`, `docker=27.3`,
  ядра, память. Человек их не трогает;
- **объявленные** пишет человек: `role=pg-runner`, «это железо под
  нагрузку». Агент их не трогает.

**Готовности «отвечает по ssh» у машины нет.** Доказательство её
существования одно — подключившийся агент. Одно доказательство вместо
двух, и оно то самое, которое нужно: не «ssh отвечает», а «выполнять есть
кому».

**Установка из кластера — опция, а не принцип.** Есть доступ — оператор
дошёл по координатам заявки и настроил, это удобно. Нет доступа — скрипт
руками или через user-data, и это нормальный режим, а не деградация. Ещё
вариант: установку выполняет **любой агент, который до машины достаёт**, —
это обычный шаг с другой целью, а не новое понятие.

Отсюда честное следствие: **первого агента в сети ставит человек или
облако.** Дальше сеть обслуживает себя сама.

### Выбор машины и аренда

**Выбор — `metav1.LabelSelector` кубера как есть**: `matchLabels` и
`matchExpressions`. Знакомо всем, писать нечего, и разницы между
обнаруженными и объявленными метками для селектора нет.

**Аренда — это владение с концом**, а не новый механизм. Прогон занимает
машину, занятая не видна в свободных, конец прогона отпускает. Нужна с
первого дня: перф-тест на машине, где в этот момент кто-то ещё что-то
делает, даёт неверные цифры, и об этом никто не узнает.

**Селектор отвечает «какие подходят», а не «какие я взял».** Недостающее —
протокол захвата, и это не планировщик:

- занять записью с `CAS`: два прогона выбрали одну машину — выигрывает
  один, второй получает конфликт и повторяет;
- брать **в фиксированном порядке** (по имени), иначе два прогона возьмут
  по половине нужного и встанут навсегда;
- **всё или ничего**: не собралось — отпустить взятое и повторить;
- повторять до срока — повтор даёт Temporal.

Ни упаковки, ни приоритетов, ни вытеснения. Сотня строк.

**Анти-аффинность при эксклюзивной аренде получается сама:** взятая машина
исчезает из свободных, значит вторая и третья будут другими по построению.
Она нужна только там, где машины делят, а мы делить не собирались.

Поэтому **в первый кусок идут селектор и аренда**, а `taints`,
`tolerations` и анти-аффинность ждут, пока не появится дележ.

**Автомасштабирования пула не будет.** Свободных не хватило — пайплайн
создаёт машину сам, потому что он программа: это строчка кода, которую
видно и можно отладить, а не политика планировщика с параметрами.

### Чем пользуется пайплайн: ровно три источника

**Любой ресурс любого провайдера Crossplane.** Облака, `provider-helm`,
`provider-terraform` (то есть всё, что умеет terraform),
`provider-kubernetes` (объект в любом другом кластере). В коде нет ни
списка поддерживаемых облаков, ни `run.Machine`: есть
`pipeline.Apply(run, имя, объект)`, где объект — любой типизированный CR.
Сменить yandex на aws — сменить импорт и структуру; наш код, операторы и
SDK не меняются.

**Наши виды.** `Run`, `Stand`, `MachineIntent`, `Machine`, `Artifact`,
`Pipeline`, `PipelineRevision` — механика самой системы, а не ресурсы
мира.

**Конструкции выполнения на агенте.** Команда и шаг. Записями они **не
являются**: это сотни короткоживущих объектов на прогон, и мы сами убили
бы кластер, на котором стоим. История шага — в Temporal; записи есть
вокруг него (машина, заявка, аренда), но не на каждое выполнение.

Своих контроллеров под чужие домены мы не пишем никогда. Не хватает
ресурса — это провайдер, а не наша задача: писать это самим — второй
заход на ошибку с apimachinery, только дороже.

**В нашем кластере живут только наши виды и виды Crossplane.** Всё
остальное — CNPG, Strimzi, что угодно — существует лишь как **содержимое**,
которое едет наружу внутри `Object` провайдера kubernetes. Плоскость
управления не место для нагрузки: соседи по кластеру портят цифры
перф-теста, а мы этот тест и обслуживаем.

### Мы не заводим понятий про чужие ресурсы

Понятия «целевой кластер» у нас нет и быть не может: чужой CR — это запись
с именем и готовностью, и **узнать, что она «кластер», нечем**. Kubeconfig
достаётся способом, который знает провайдер, а не мы.

Поэтому положить что-то в другой кластер — это обычный `Object` чужого
провайдера, где пользователь сам называет `ProviderConfig`, а мы даём
ровно одну мелочь: сериализацию типизированного значения в поле манифеста.

```go
pipeline.Apply(run, "pg", &kubernetesv1.Object{
	Spec: kubernetesv1.ObjectSpec{
		ProviderConfigRef: kubernetesv1.Ref("target-cluster"),
		ForProvider: kubernetesv1.ObjectForProvider{
			Manifest: pipeline.Manifest(&cnpgv1.Cluster{
				Spec: cnpgv1.ClusterSpec{Instances: 3},
			}),
		},
	},
})
```

Правило общее: **каждый раз, когда хочется вывести что-то о природе чужого
ресурса — этого делать нельзя, пользователь скажет явно.** Оно заранее
закрывает целый класс соблазнов: «понять, что это база», «вывести адрес»,
«догадаться, куда подключаться».

Следствие для требований: тип попал в **`Apply`** — применяется у нас,
идёт в требования; тип попал в **`Manifest()`** — это содержимое, у нас
его быть не должно, в требования не идёт. Различает не догадка о природе
ресурса, а то, **в какую функцию отдали значение**.

### Готовность произвольного ресурса

По умолчанию — условие `Ready=True`: так делает Crossplane и большинство
операторов, написанных по конвенции.

Экзотика — **обычным циклом в коде**, потому что пайплайн это программа, а
`Sleep` у Temporal durable:

```go
for {
	pg := pipeline.Get(run, cluster)
	if pg.Status.Phase == "healthy" { break }
	run.Sleep(10 * time.Second)
}
```

Ни DSL, ни языка предикатов. Декларативное условие можно добавить потом,
когда надоест писать цикл.

### Агент тонкий, полезности — библиотеки

`agentdocker.Install`, `pg.Install` и сотни таких — **не код агента**, а
обычные библиотеки на стороне пайплайна, складывающие примитивы:

```go
func Install(run pipeline.Run, on pipeline.Target) Installed {
	if v := run.On(on).Command("docker/look", exec.Argv("docker", "version")); v.Code == 0 {
		return Installed{Version: v.Stdout}
	}
	run.On(on).Command("docker/install", exec.Script(installScript))
	run.On(on).Facts()                       // перечитать, что теперь на машине
	return Installed{...}
}
```

Будь это кодом агента, каждая новая полезность означала бы релиз агента и
обновление всего парка — а парк обновляется больно и разъезжается по
версиям в первый же месяц. Так — это обычные Go-пакеты, которые публикует
кто угодно, не спрашивая нас и не попадая в наш релизный цикл.

**Агент умеет пять вещей**, и это activity с фиксированным контрактом:

- `Exec` — запустить процесс: argv, окружение, каталог, stdin, таймаут,
  поток вывода, код возврата;
- `Put` / `Fetch` — положить файл на машину и забрать с неё (забрать —
  сразу в хранилище по предподписанной ссылке, мимо управляющего);
- `Stat` — дешёвая проверка «есть/нет»;
- `Signal` — прибить процесс, когда прогон отменяют;
- `Facts` — рассказать о себе и **обновить** обнаруженные способности.

Даже «нужен нативный код на машине» это не ломает: доставить бинарь и
запустить — те же два примитива, системы плагинов не нужно.

**Контракт примитивов — самая консервативная часть системы.** Парк
обновляется медленно, значит менять его надо реже всего, версионировать
явно, и старые агенты обязаны продолжать работать.

#### Сходимость живёт в программе, а не в агенте

«Посмотри, если нет — поставь» — это обычный `if` по результату шага.
Реконсилер на агенте означал бы своё желаемое состояние, своё хранилище и
свои повторы **на каждой машине**, то есть вторую плоскость управления,
размазанную по парку. Цикл в воркфлоу даёт то же самое даром: он durable,
виден в истории, переживает падения, и на машине для него ничего не нужно.

Память по именам делает повтор дешёвым: `docker/look` уже выполнялся —
вернётся записанный результат, второй раз на машину никто не полезет.

**У `Machine` нет спеки, и не будет.** Желаемое состояние машины нельзя
материализовать заранее: оно возникает **в ходе программы**, когда та
доходит до `docker.Install`. Записать его в спеку значило бы знать
требования до того, как пайплайн их выразил, — то есть повторить их
вторым местом и следить, чтобы совпадали.

Значит `Machine` — только метки и taints от человека и факты от агента.

«Держать машину в заданном состоянии постоянно» при этом никуда не
девается — но это **пайплайн, который пишет пользователь**: пробежать по
машинам и поставить, что надо. Ни спеки, ни контроллера, ни нового
понятия; та же программа, те же шаги, та же память по именам. И это ровно
то, чем мы торгуем, а не то, что мы делаем за пользователя.

#### Способность — контракт между обёртками

Одна даёт, другая по ней выбирает:

```go
for _, node := range nodes { docker.Install(run, node) }   // даёт docker=27.3

runners := pipeline.Machines(run, has("docker"))           // выбирает
for _, node := range runners { docker.Run(run, node, spec) }
```

- **даёт** — обёртка кончается `Facts()`, агент видит докер и пишет метку;
- **выбирает** — обычный селектор по меткам;
- **требует** — обёртка в начале проверяет и падает с внятным «на этой
  машине нет докера».

**Состояние живёт на машине, запись его отражает** — и никогда наоборот.
Поэтому обёртка не пишет способность сама, а просит агента перечитать
факты: тогда запись не может соврать. Сняли докер руками — следующий обзор
это увидит; а если бы метку ставила обёртка, запись утверждала бы то, чего
давно нет, и выбор ломался бы молча.

Гонки нет: `Facts()` — activity, а завершённая activity означает, что
запись уже сделана. К моменту возврата из `Install` метка на месте.

Селектор кубера умеет `Exists`, `In`, `NotIn`, но **не сравнивает версии**:
«есть докер» — селектором, «докер не ниже 24» — чтением фактов и обычным
сравнением в коде. Грубый отбор селектором, точная проверка кодом.

**Обёртки пишутся так, будто система голая.** То, что установка иногда
обнаружит уже поставленное и ничего не сделает, — бонус, а не требование к
автору.

#### Правила для авторов библиотек

**Имена шагов выводятся детерминированно** из того, что дал пользователь:
обёртка из трёх команд называет их `docker/install`, `docker/verify`,
`docker/start`. Иначе при перезапуске прогона память по именам не сработает
и шаги выполнятся заново — а нарушение тихое.

**Обёртка не ходит в сеть сама.** Она исполняется в воркфлоу, там
детерминизм: только через примитивы.

### Шаг по умолчанию — не запись

Записи только у того, что имеет владельца и конец: машина, агент,
установка, стенд, артефакт. «Выполнить команду», «прогнать тест» —
activity, живут в истории Temporal.

Иначе каждый прогон — сотни короткоживущих объектов в etcd, и мы убьём
кластер, на котором стоим. Ровно то, обо что споткнулись Tekton и Argo.

Исключение: **результат, который потребляют другие записи, обязан лечь в
запись.** Метрики, на которые смотрит человек или следующий прогон, —
артефакт со ссылкой.

Цена, которую надо уметь объяснить одной фразой: `kubectl` показывает мир,
Temporal показывает ход. Два места для двух разных вопросов.

### Пайплайн ничего не трогает сам

Воркфлоу детерминирован — ему физически нельзя ходить в сеть. Значит
`Apply` в коде пайплайна это не вызов кубера, а activity, и выполняет её
**системный воркер**, а не образ пайплайна:

- образ пайплайна не имеет доступа ни к кубу, ни к облаку, ни к секретам —
  он только решает;
- credentials живут в одном месте;
- сырой или чужой пайплайн не может ничего, кроме объявленных шагов.

Системный воркер работает с `unstructured`: объект приходит к нему уже как
JSON. Поэтому **новый провайдер не требует пересборки ничего нашего** —
пользователь ставит provider-aws, пишет `awsv1.Instance`, наши бинари те
же.

### Ожидание готовности — сигналом от оператора

Не блокирующей activity: машина, которая едет три минуты, держала бы слот
воркера. Оператор и так видит переход в готовность — он же и будит
воркфлоу.

Запасной вариант, если сигналы окажутся неудобны: activity, которая
смотрит и шлёт heartbeat. Проще, дороже слотами.


### Код пользователя выполняется на его стороне

**Принято: код пайплайна недоверенный.** Он произвольный, его пишет кто
угодно, и внутри него можно сделать что угодно. Поэтому он не выполняется
в нашем кластере — ни в каком виде.

Выполняет его воркер на стороне пользователя: его машина, его runner, его
кластер, или машина, на которой уже стоит наш агент. Нам всё равно, какая
именно; нам важно, что это **не наша**.

Прежнее решение — оператор поднимает `Deployment` на каждую ревизию —
**отменяется целиком**. Оно закрывало настоящую дырку («образ есть, а
запускать его некому»), но закрывало не тем: превращало «положить
пайплайн в систему» в «выполнить произвольный код внутри управляющего
слоя».

**Наружу смотрит два API, и это разные API.** Одно — для человека и его
лиц (CLI, потом TUI и UI): пайплайны, прогоны, записи. Второе — для
кода: «дай задачу, прими результат». Второе вполне может быть самим
Temporal, но с проверкой подлинности и правами, а не так, как сейчас.

**Цена названа честно.** Прогон переживает падение чего угодно, но не
двигается, пока нет воркера пользователя. История в Temporal цела, работа
продолжится, когда воркер вернётся, — но «прогон идёт сам по себе, пока
все спят» перестаёт быть правдой для шагов, которые считает сам пайплайн.
Шаги на машинах этим не затронуты: их выполняют агенты.

#### Что из этого следует чинить, и это дырки, а не задачи

**Полномочия не спрашиваются, а заявляются.** `Apply` принимает владельца
из аргументов activity. Воркфлоу говорит, от чьего имени создать запись, и
мы верим. Недоверенный код обязан не иметь такой возможности: владелец
должен выводиться из того, кто на самом деле выполняет воркфлоу, а не из
того, что он о себе сказал.

**Общая очередь — путь эскалации.** У воркера пайплайна есть клиент
Temporal и адрес. Значит, он может подписаться на нашу системную очередь
`graphene-system` и получать наши `Apply` и `Teardown` — задачи, которые
выполняются нашими правами в кластере. Это верно и когда код крутится на
машине пользователя: дело не в том, где он крутится, а в том, что у него
есть клиент с нашими полномочиями.

Обе закрываются вместе с правами Temporal — это M7, и он от этого
укрупняется, а не остаётся прежним.


### Работа не живёт в воркфлоу

Посмотреть на SDK и увидеть: в нём нет ни одной конструкции, которая
что-то **делает** в воркфлоу. `Apply` просит запись, `On(...).Command(...)`
выполняет на машине, `Await` спит, `Teardown` сносит. Это не случайность —
это инвариант, и его надо соблюдать, а не подразумевать.

Temporal наказывает за нарушение сам: код воркфлоу выполняется
кооперативно на одном логическом потоке и **переигрывается** из истории
при каждом восстановлении. Тяжёлый цикл ловит таймаут задачи воркфлоу,
попадает в повтор и считает заново на каждом повторе. Пайплайн вешает сам
себя, и это видно сразу, а не когда-нибудь.

**Законная дверь для вычислений — `pipeline.Do`.** Без неё человек упрётся
и начнёт считать прямо в воркфлоу, потому что больше негде:

```go
report := pipeline.Do(run, "разобрать-отчёт", func() Report {
    return perf.Parse(bench.Stdout)   // обычный Go, сколько угодно тяжёлый
})
```

Это activity на воркере пользователя. Отсюда бесплатно: воркфлоу не
блокируется, результат ложится в историю и при переигрывании не считается
заново, падение посреди счёта переживается, и в трассе видно, что этот шаг
занял восемь минут — а не «прогон почему-то стоял». Цена та же, что у
команд: выполняется **не менее одного раза**, значит либо идемпотентно,
либо помечено одноразовым.

### Отклонено: сериализовать программу в граф операций

Заманчивый вариант: выполнить код пользователя у него, получить граф
операций, выполнить граф у нас. Так живут Terraform и Pulumi, так жила
прежняя раскладка с KCL. Отклонено по двум причинам, и первая важнее.

**Граф заранее несовместим с ветвлением по результатам.** Вот ради чего
всё затевалось:

```go
bench := pipeline.On(run, nodes[0]).Step("bench", perf.Bench(p))
if bench.P99 > perf.Threshold {
    run.Keep(24 * time.Hour)
    return fmt.Errorf("деградация: p99 %v", bench.P99)
}
```

`bench.P99` не существует, пока шаг не выполнился. Граф, построенный до
начала, не может содержать эту ветку: значение появится в середине его же
исполнения. Значит, программа обязана быть **жива во время прогона** —
именно поэтому у Pulumi есть `apply()` с колбэком и именно поэтому
программа Pulumi не умирает на время `up`. Граф заранее возможен только
ценой отказа от ветвления, то есть возврата к шаблону с `if`.

**А задачу, ради которой его предлагают, он не решает.** Произвольный код
никуда не девается — он просто выполняется во время вычисления графа.
Цикл, жгущий процессор, жжёт его на этапе `preview` у Pulumi ровно так же.

Наша нынешняя форма и есть модель Pulumi, только программа «жива» дёшево:
воркфлоу Temporal — это живая программа, а история — тот самый граф
операций, записанный **по факту**, а не предсказанный заранее. И она
восстанавливается после смерти процесса, чего Pulumi не умеет.

### CI как услуга включается изоляцией, а не сериализацией

Кнопка в UI без воркера на стороне клиента означает, что воркер держим мы.
Тогда нужно то же, что нужно любому CI как услуге, и ничего сверх:

- воркер в песочнице на арендатора: без учёток, наружу только Temporal и
  только со своими правами;
- лимит процессора и памяти — тяжёлый цикл жжёт **свою** квоту;
- таймаут задачи воркфлоу как предохранитель (он уже есть);
- учёт, потому что за процессор кто-то платит.

Ни один пункт не требует графа. Все требуют работы над правами — то есть
M7, который от этого укрупняется.

### Воркер пользователя обязан быть всегда включён

Обещание «единожды попав в систему, пайплайн запускается из UI» требует,
чтобы ревизию **кто-то обслуживал постоянно**. Ноутбук разработчика — это
режим разработки, а не эксплуатации.

Требование звучит не «на машине разработчика», а **«вне контура доверия
управляющего слоя»**. Так живут self-hosted runners GitHub и агенты
Buildkite: кнопка создаёт прогон, выполняет парк заказчика.

Где именно — выбор, который остаётся открытым: машина с нашим агентом
(красивее всего — такие машины уже есть как понятие и всегда включены),
их собственный кластер по нашему манифесту, или их runner.

Если воркера нет — прогон **не падает, а ждёт**. Запись создана, история
цела, работа продолжится, когда воркер вернётся.

### `defer` с отвязанным контекстом

В Temporal при отмене обычный контекст уже мёртв, и наивно написанный
`defer` не выполнится — то есть главное обещание не сработает ровно в том
случае, ради которого оно есть.

`run.Teardown` внутри переключается на отвязанный контекст. Это обязано
быть в библиотеке, а не в пользовательском коде.

### Секрет — ссылкой до самого конца

В воркфлоу и в истории только имя. Значение разрешает тот, кто им
пользуется: агент — у себя, системный воркер — у себя, и обратно не
возвращает.

Ловушка, о которой вспоминают поздно: **аргументы и результаты activity
пишутся в историю Temporal** и лежат там весь retention. Секрет, переданный
значением, утекает не в лог, а в историю прогонов — туда, куда все ходят
смотреть.

### Агент приходит сам; мы никогда не ходим на машину

**Сетевого доступа от кластера к машинам нет — считаем так всегда.**
Управляющее обязано быть доступно снаружи, значит единственное направление
связи — наружу от машины.

Установка — один и тот же скрипт, чем бы машина ни была:

```
curl -fsSL https://ctrl.example/install | bash -s -- \
    --token <…> --control <адрес> --name <имя агента>
```

Внутри: скачать бинарь под свою архитектуру, записать юнит, запуститься,
дозвониться наружу, представиться и начать продлевать аренду. Появление
записи `Machine` — **это и есть доказательство**, что машина работает и
выполнять на ней есть кому; отдельной «готовности агента» не существует.

Скрипт отдаёт SDK, а **кладёт его пользователь**. Мы не знаем, как у
провайдера называется поле для user-data, и не должны: SDK возвращает
строку, пользователь пишет её в свою же спеку. Провайдеро-независимость от
этого не страдает, а укрепляется — мы физически не можем полезть в чужую
спеку.

Два пути доставки, один скрипт:

**Облачная машина.** Скрипт идёт в user-data ресурса провайдера. Никакого
входящего доступа не нужно вовсе.

**Существующая машина, до которой есть ssh.** Тот же скрипт, другой
доставщик: пишется `MachineIntent` с координатами и текстом скрипта, а
доставляет его оператор — или любой агент, который до этой машины
достаёт.

```go
join := agent.Install(run, "legacy-1")   // очередь известна сразу

pipeline.Apply(run, "legacy-1", &graphenev1.MachineIntent{
	Spec: graphenev1.MachineIntentSpec{
		Address: "10.0.0.7:22",
		Auth:    graphenev1.SSHKeyRef("fleet"),
		Script:  join.Script(),          // тот же текст, что ушёл бы в user-data
	},
})

// Ждать нечего: шаги адресуются очереди join, и очередь сама и есть
// ожидание.
pipeline.On(run, join).Command("install-pg", …)
```

Симметрия с облачным путём полная: там скрипт кладёт пользователь в свою
спеку, здесь — в заявку; handle и очередь в обоих случаях известны сразу,
и ни в одном не нужно ждать агента отдельно.

Ssh-доставка — **единственное место, где мы соединяемся к машине**, и
только туда, куда пользователь сам дал координаты и ключ. Не дотянулись —
остаётся человек или user-data, и это не деградация.

**Известная дырка, записана осознанно.** Токен в скрипте попадает в спеку
ресурса — то есть в `etcd` — и в историю Temporal, где живёт весь
retention. Это противоречит правилу «секрет не в спеке». Сейчас так, потому
что закрывать это до первого работающего прогона — безопасность ради
безопасности. Направления, когда дойдут руки: одноразовый талон вместо
токена, который сгорает при первом использовании; или удостоверение из
метаданных инстанса, которое не лежит нигде вовсе.

**Имя очереди выдаётся при установке и уникально по построению**
(`node-0-3f2a1b`), а не выводится из имени машины. Тогда пересозданная под
тем же именем машина ничего не ломает: старый агент читает **свою старую**
очередь, в которую больше никто не пишет, и умирает от бездействия.

Очередь принадлежит **установке**, а не имени, — и отсюда сама собой
получается разница двух похожих случаев: перезагрузка машины оставляет ту
же очередь (файл настроек на месте), пересоздание даёт новую.

Память по именам не мешает: `agent.Install(run, "node-0")` — activity с
ключом по имени, при перезапуске прогона вернётся тот же handle, а не
выпустится второй пропуск.

Чистить очереди не нужно: в Temporal они неявные, пустая очередь — это
просто отсутствие поллеров.

**Бинарь агента раздаёт управляющее** со своей же точки: тогда версия
агента всегда совпадает с версией системы и одной движущейся частью
меньше. Если раздача мегабайтов окажется заметной — вынесем в реестр, это
обратимо.

Требование к развёртыванию: **машина должна доставать до двух адресов** —
до управляющего и до Temporal. Больше ей ничего не нужно, и внутрь неё не
нужно ничего.

### Артефакты, логи, метрики, трассы

**Мы храним ссылки, а не данные.** Всё, что растёт с числом прогонов,
живёт снаружи; в записи — где оно и чем его искать.

#### Артефакты

Вид `Artifact`: имя, дайджест, размер, тип, ссылка на байты. Годится и как
выход прогона, и как **вход**: сборка положила бинарь, выкатка его взяла —
так «build → deploy» ложится в ту же модель без новых понятий.

**Заливает агент, напрямую в хранилище.** Байты у него — отчёт лежит на
машине. Тащить их через управляющее нельзя (это гигабайты через центр),
давать агенту постоянный ключ от хранилища тоже. Системный воркер выдаёт
**предподписанную ссылку**, агент кладёт по ней и отчитывается дайджестом.

**Артефакт не принадлежит прогону.** Иначе снос стенда унесёт отчёт, ради
которого всё запускали. У него свой срок хранения, и он переживает то, что
его породило — явно объявленным владельцем и сроком, а не исключением.

**Срок хранения — три уровня с наследованием, все необязательные:**
настройка инсталляции → политика на `Pipeline` → поле у самого артефакта.
Ближайшее заданное выигрывает; «не задано» значит «наследовать», а не
«вечно». Значение по умолчанию в инсталляции обязано быть **конечным** —
иначе счёт за хранилище растёт молча.

#### Логи, метрики, трассы — мы даём трубу, а не хранилище

Агенту и шагу подсовывается **OTLP-эндпоинт** и атрибуты: id прогона, имя
шага, машина. Всё, что процесс пользователя пишет сам, оказывается
связанным с прогоном — не потому что мы что-то перехватываем, а потому что
задали контекст.

В записи — **куда писали** и чем это искать: адрес приёмника, id трассы,
интервал, метки. UI ставит ссылку в чужую графану и ничего не хранит у
себя.

Исключение ради удобства: **хвост вывода упавшей команды** (килобайты)
едет в результат шага, чтобы в сообщении об ошибке было видно, что
случилось, а не «смотри в логи». Полный вывод — артефактом или в приёмник.

#### Хранилище и приёмник — по выбору пользователя

И то и другое: либо в поставке, либо снаружи. Это дёшево ровно потому, что
у обоих **стандартный протокол** — S3-совместимый API и OTLP. Никаких
вендорских SDK и никакой развилки в коде: адрес и учётные данные,
остальное одинаково.

#### Наблюдаемость самой системы — с нулевого дня, той же трубой

Наши операторы, системный воркер и агент пишут в тот же OTLP, что и
пользовательский код. Не отдельный механизм для себя.

Что должно получиться сразу: **одна сквозная трасса на прогон** — `Run`
создан → воркфлоу стартовал → activity → `apply` записи → готовность →
шаг на агенте → снос. У Temporal для этого есть перехватчики, у
controller-runtime — метрики из коробки.

Проверка, что это не для галочки: вопрос **«почему прогон стоял восемь
минут»** должен отвечаться одной трассой, а не сопоставлением трёх логов по
времени.

#### Результат прогона — в статусе, с потолком

Симметрия: **параметры — типизированный вход, результат — типизированный
выход.** Оба объявлены типом в коде пайплайна, схема обоих публикуется
ревизией, UI рисует их из одного источника, оба видны в записи.

Ограничитель обязателен: **в статусе выводы, а не данные.** Жёсткий предел
на размер прямо в CRD (единицы килобайт); не влезло — значит артефакт.
`p99`, «прошло / не прошло», ссылка на отчёт — да; сам отчёт — нет.

### Как пайплайн попадает в систему

Две записи, разделённые как `Deployment` и `ReplicaSet`, потому что задача
та же.

**`Pipeline`** — стабильное имя, хозяин, политика: срок хранения прогонов,
кто может запускать. Живёт долго, меняется редко.

**`PipelineRevision`** — неизменяемая: **дайджест** образа, схема
параметров, список требований, имя очереди. Владелец — `Pipeline`. Умирает,
когда доиграл последний прогон, который на неё ссылается.

`Run` ссылается на **ревизию**, а не на имя. Иначе обещание «прогоны
доигрывают на своём коде» не выполняется: кто-то обновит образ, и идущий
час прогон обнаружит под собой другой код.

Идентичность версии — **дайджест, а не тег.** Тег изменяем, и `latest` под
идущим прогоном — ровно та беда, которую мы обещали не допускать. Очередь
именуется по дайджесту, деплоймент воркера — по ревизии.

**Ревизию пишет человек или CI, а не порождает оператор.** Многословнее,
чем поле `image` в `Pipeline`, зато версия видна в манифесте, история
версий там, где её ищут — в гите, а откат это `git revert`.

Кто что делает:

- **человек или CI** — пишет `Pipeline` и `PipelineRevision`;
- **оператор** — поднимает деплоймент воркера на ревизию и убирает
  деплойменты тех ревизий, на которых не осталось живых прогонов;
- **воркер при старте** — публикует в статус ревизии схему параметров и
  список требований: он единственный, кто их знает;
- **оператор** — сверяет требования с `discovery` и ставит готовность.

**`Ready` у ревизии = воркер поднялся, отчитался, и всё, что ему нужно,
в кластере есть.** До этого `Run` на неё не создаётся, и человек видит
причину.

**Расписание — свойство `Pipeline`, а не отдельное понятие.** Список
записей «имя, cron, параметры»; под ним расписания Temporal, а порождает
оно обычные `Run` — вход остаётся тем же, просто запись создаёт не
человек. Отсюда и «подготовка парка по расписанию» получается сама, без
единого нового механизма.

Раз это обычные записи, применяются они чем угодно: `kubectl`, наша
команда, или GitOps — манифест рядом с кодом, CI подставляет дайджест,
Flux или Argo применяет. Ничего специального для GitOps делать не надо, он
получается сам.

**Режима «запустить локально собранный образ» не будет.** Он сводится к
настройке локального k3s с реестром, а это не наша забота: отладка идёт
через обычный push в реестр разработчика.

## Что видит человек

Четыре места хранят части ответа: куб — мир, Temporal — ход, приёмник —
логи и метрики, хранилище — отчёты. Вопрос «что с моим прогоном» сегодня
требует обойти все четыре и сложить в голове.

**Поэтому наружу выдаётся одно API, и на нём делаются все лица:** сначала
CLI, потом TUI и UI. Один контракт — трём лицам нечем разойтись.

### Три правила, без которых API становится третьей правдой

**Агрегирует, но ничего не хранит.** Всё добывается из куба, Temporal,
приёмника и хранилища. Кеш можно, базу нельзя. Проверка: **снеси его
состояние целиком — не потеряется ничего.** Как только появится «а вот это
только у нас», мы снова пишем apimachinery, теперь с веб-мордой.

**Не заводит своих прав.** В куб ходит **от имени вызывающего**, а не своим
сервис-аккаунтом. RBAC остаётся один; иначе через месяц их два, и второй
всегда шире.

**Не подменяет `kubectl`.** Записи остаются записями: `kubectl`, GitOps,
`apply` из CI работают как работали. API — добавка, а не ворота. Иначе
теряется то, ради чего брали кубер.

### Что оно обязано отвечать

- какие прогоны есть, кто запустил, на какой ревизии, с какими параметрами;
- где прогон сейчас — какой шаг, сколько уже ждёт;
- что он создал — машины, стенд, кто чем владеет, что останется после;
- **почему стоит** — не заполнена зависимость, нет свободных машин, нет
  провайдера, ждёт человека;
- куда смотреть — ссылки на трассу, логи, отчёт;
- чем кончилось — статус и артефакты;
- что можно сделать — отменить, оставить стенд, повторить, ответить на
  ожидание.

**Четвёртый пункт — тот, ради которого всё.** Сегодня «почему оно стоит»
узнаётся обходом четырёх мест; если мы отвечаем на это одним экраном,
продукт оправдан, даже если больше в нём ничего нового нет.

### Потоком, а не опросом

«Видно, что происходит» значит поток: у куба есть watch, у Temporal —
подписки. Иначе три лица начнут опрашивать раз в секунду и станут третьим
источником нагрузки на etcd.

Отсюда **gRPC со стримами**, для браузера тот же контракт через grpc-web
или connect.

### CLI — две половины, и только одна из них про API

- **локальная**: `generate`, `build`, `push` — исходники, тулчейн Go,
  сборщик образов. Кластер не участвует; единственная точка касания —
  запись `PipelineRevision` в самом конце. CI работает так же: раннер это
  просто ещё одна машина разработчика.
- **удалённая**: `run`, `watch`, `logs`, `cancel`, `keep` — чистый клиент
  API.

Отправлять исходники в кластер, чтобы он собрал, — отдельный продукт со
своими сборщиками, кешем и очередями. Мы его не строим.

Стоит посмотреть на `ko`: он собирает Go-бинарь сразу в образ без
Dockerfile, а образ пайплайна ровно это и есть — тогда пользователю нечего
писать и нечего забыть.

**В первый кусок входит только CLI.** TUI и UI — идеи; API при этом
проектируется полным сразу, чтобы им потом нечего было доделывать.

### Где будет больно

**Права Temporal.** В кубе impersonation решает всё, у Temporal модель прав
беднее. «Этот человек видит только свои прогоны» придётся обеспечивать нам,
на уровне API, при выборке. Единственное место, где вторая модель прав
всё-таки появляется — записано заранее, чтобы не обнаружить при первом
чужом пользователе.

## Языки: сейчас только Go

Пайплайн пишется на Go, типы провайдеров берутся **из их же Go-пакетов**,
никакой генерации нет. Это решение на сейчас, а не навсегда, и вот что за
ним стоит.

**Мультиязык почти бесплатен там, где кажется дорогим.** Temporal уже
мультиязычен: воркфлоу на Python вызывает activity, реализованную на Go, —
они общаются очередью и сериализованной нагрузкой, а не вызовами функций.
Значит всё тяжёлое — запись в куб, ожидание, артефакты, секреты, аренда —
пишется **один раз на Go** и обслуживает пайплайны на любом языке.

На каждый язык нужно немного: заглушки (`serve`, `apply`, `await`,
`on/command/step`, `artifact`, `keep`, `teardown`, `get`, `sleep`) — каждая
кладёт в очередь имя и аргументы; чтение параметров в схему (теги в Go,
`dataclass` в Python, `zod` в TS); и **генератор типов из CRD**.

**Дорого именно последнее, и поэтому мультиязык отложен.** Go-структуры
провайдеров существуют только для Go — питонист их не импортирует никак.
Значит второй язык требует порождать типы из схем OpenAPI, лежащих в CRD.
Задача решаемая (`cdk8s import` делает это для TS, Python, Java и Go;
`crd2pulumi` — для Pulumi), но это отдельный кусок работы со своими
шероховатостями: `x-kubernetes-preserve-unknown-fields`, `int-or-string`,
`oneOf`, поля без схемы вовсе.

Когда дойдут руки, источник типов — **не «провайдер», а CRD, откуда бы он
ни приехал**: пакет Crossplane (`oci://`), релизный yaml (`https://`),
чарт (`helm://`), свой файл (`file://`), живой кластер для разведки. Свой
CRD пользователя при этом не особый случай, а одна из строк. Плюс фильтр по
видам, иначе большой провайдер породит мегабайты кода, которые никто не
читает.

И условие, без которого второй язык станет калькой с первого: **контракт
SDK должен быть документом раньше, чем вторым SDK.** Что такое шаг, что
значит имя, что попадает в требования, что делает `Teardown` при отмене —
это описание протокола, а не свойство Go. Проверка простая: если для
второго языка понадобилось что-то, кроме перевода типов и десятка вызовов,
модель протекла.

## Требования пайплайна и ранний отказ

Пайплайну нужны CRD провайдеров, которых в кластере может не быть. Об этом
надо сказать как можно раньше — и не имея ни одного `if` по облакам.

**Источник истины — типы, которые пайплайн использует.** Из них выводится
и сопоставление «Go-тип → GVK» (нужное для сериализации), и список
требований. Один источник, два выхода.

**Четыре рубежа:**

1. **Регистрация артефакта.** Воркер стартовал — публикует в
   `Pipeline.status.requires` список GVK. Оператор сверяет с тем, что
   умеет кластер (`discovery`), и ставит неготовность с причиной: «нет
   `compute.yandex.crossplane.io/v1beta1 Instance` — поставьте
   provider-yandex».
2. **Создание `Run`.** Вебхук смотрит на `Pipeline`: требования не
   удовлетворены — запуск не создаётся, человек видит текст сразу.
3. **Первый `apply`.** Кубер отвечает `no matches for kind`, мы переводим
   в ту же фразу. Нужен: CRD могли снести между проверкой и запуском.
4. **Версии.** `discovery` даёт точные GVK, поэтому сообщение может быть
   «есть `v1beta2`, а код просит `v1beta1`» — самая частая настоящая беда.

Нигде нет ни списка облаков, ни ветвления по ним: работа идёт с GVK, имена
приходят из типов пользователя.

**Чего это не ловит:** наличие CRD ≠ работоспособность. Нет
`ProviderConfig` с ключами — записи создадутся и никогда не станут готовы.
Готовность провайдера — тоже часть требований, и её надо проверять, а не
только присутствие вида.

**Ограничение, названное вслух:** если тип ресурса выбирается в рантайме
(два облака, какое — решает параметр), статически видны оба, оба попадут в
требования, и для запуска понадобятся оба провайдера — даже если прогон
пойдёт по одной ветке.

### Про `AddToScheme` — исследуется в процессе написания кода

Сопоставление «Go-тип → GVK» в самом значении отсутствует: `TypeMeta` у
литерала пуст, группа и версия лежат переменной в пакете провайдера.
Глобального реестра схем нет и быть не может: Go не умеет перечислять
инициализации импортированных пакетов, поэтому в каждом контроллере на
свете лежит написанный руками блок `AddToScheme`.

**Пользователь писать его не должен** — это второе место, которое молча
разъедется с первым.

Намеченное решение: `graphene generate` проходит по исходникам с полной
информацией о типах, находит типы, ушедшие в `Apply`, и порождает
`zz_generated_scheme.go` с регистрацией; файл **коммитится**, CI сверяет
свежесть. Пакет не по конвенции (без `AddToScheme`) — **ошибка сборки** с
указанием, что дописать, а не отказ в рантайме.

**Это гипотеза, а не решение.** Проверяется первым же кодом: как ведут
себя реальные пакеты Crossplane, хватает ли `go/packages`, что делать с
типами, полученными не литералом. Возможные исходы — от «работает как
задумано» до «регистрацию отдаёт сам воркер при старте, а сборка только
проверяет». Выбор делается на коде, не здесь.

Отдельно: генерация типов **снимает этот вопрос целиком** — свой
сгенерированный тип несёт GVK внутри, и ни реестра схем, ни прохода по
исходникам не нужно. Но генерация отложена вместе с мультиязыком, поэтому
гипотеза снова в силе.
